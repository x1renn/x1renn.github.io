网络相机图传与多相机集中管理系统

相机采集端

封装工业相机发现、连接、取流及参数读写流程，按设备编号维护采集上下文；处理连续采集、外部触发和软件触发模式，将相机回调输出的图像交由处理线程。

  1. 发现是枚举设备；连接是取得设备句柄；取流是启动采集并接收图像；参数读写是通过设备接口读取或修改真实参数。
  2. 每台设备一份 CameraContext：设备编号、SDK 句柄、状态、采集模式、实际参数、图像格式、帧号、原图队列和停止状态。以设备序列号建立稳定的 deviceId 映射。设备状态固定为 Closed → Opened → Grabbing → Stopping → Opened，失败进入 Failed。同设备的 SDK 开停与参数命令交给采集控制执行线程串行处理；SDK 图像回调只做数据交接，不与网络线程并发修改句柄。
    模式 谁决定出图 例子
    连续采集 相机按设置节奏持续出图 调焦时持续看画面
    外部触发 外部信号满足触发条件 光电传感器检测到零件
    软件触发 软件发触发命令 点击“拍一张”
    为什么不能把重活都放在回调里？
    回调像相机交货的窗口。转换、编码、网络发送耗时不稳定，如果占着回调不返回，会延迟 SDK 调度或缓冲归还，后续图像可能堆积或丢失。耗时编码与不可预测的网络等待会占住 SDK 的交付线程、延迟缓冲归还。
    回调只做：检查结果 → 记录元数据 → 取得可靠内存所有权 → 放入有界队列 → 返回。

图像传输协议

设计控制报文与图像报文格式，定义消息类型、设备编号、负载长度、帧序号和时间戳；通过接收缓冲区与解析状态机处理半包、粘包及连续报文，使用请求编号关联控制应答。

TCP 字节流＋固定 34 字节公共头＋变长包体。整数使用大端序逐字段序列化。
图像包体固定为“1 字节关键入口标记（IDR）＋一张完整 H.264 图像的访问单元（Access Unit）”

字段 类型／字节数 作用 使用约定
消息类型 type uint16／2 区分操作与数据 设曝光、应答、流重置、编码参数、图像等
设备编号 deviceId uint32／4 标明目标相机 设备稳定标识
负载长度 payloadLength uint32／4 包体长度，不含公共头 总长度＝34＋负载长度
帧序号 frameSeq uint64／8 标识图像 控制消息不用时置 0
时间戳 timestamp uint64／8 图像媒体时间 本次采集开始后的微秒数；控制不用时置 0
请求编号 requestId uint64／8 关联控制请求与应答 请求从 1 递增，普通图像置 0

  1. 半包就是没收全，粘包就是多条业务报文同时在缓冲中；连续报文指完整一条后循环看下一条，最后不完整的留到下次。

    损坏恢复：检测到非法类型、异常长度或无法解析的包体，立即停止处理，断开并清空状态。重连后重新订阅、收到参数并等 IDR。若需原连接内重同步时，需扩展协议（魔数）再进行校验。

  2. 状态机两个： WaitHeader → WaitBody → WaitHeader，确认完整头，检查类型和长度，再等完整体；处理完消费整条，继续解析，数据不够就退出本轮回调。

内镜图像增强

开发降噪、亮度调整、对比度拉伸和色彩校正处理，使用双边滤波抑制图像噪声并保留黏膜边缘；通过 LUT 完成像素映射，并结合组织区域掩膜排除暗区、反光区和无效边缘。

输入是 1920×1080、8 位 NV12、BT.709 有限范围。先按 709 矩阵把 Y=16～235、UV=16～240 转成 RGB8 的 0～255 数值，再依次执行：原图生成掩膜 → 双边滤波 → 三维 LUT 色彩校正 → 颜色转换（RGB → YCrCb/YUV） → 一维 LUT 亮度（Y1）调整 → CLAHE 对比度增强(Y2) → 恢复 RGB → 掩膜融合。

掩膜从未经增强的原图生成，避免先提亮后把暗区误判成有效区。双边滤波先抑制细小波动，随后亮度、对比度变换不会先把噪声放大。色彩校正采用三维 LUT 色彩校正，放在亮度调整之前。后两项选择性启用，先亮度后 CLAHE。

降噪基线采用原分辨率、邻域直径 5、sigmaColor=20、sigmaSpace=2，不沿用旧美颜模块的宽高各缩小到四分之一。它优先减少细节损失；处理成本由有效视野 ROI 和 SIMD/GPU 实现控制，不靠大幅降采样换速度。例如暗处原来有 2 个灰度级的噪声，先乘以 3 倍对比度后就变成 6 个灰度级，会更显眼。反过来先抑制小波动，再适度拉开对比度，更容易控制观感。但不能为了“干净”抹掉细小纹理；需要同时保留未增强画面供对照。

  1. 双边滤波降噪：距离近 + 颜色相近的像素权重大；距离远或颜色差异大的像素权重小。抑制了边缘模糊，保留边界。
  2. 亮度调整：一维 LUT，以原亮度 Y（0～255）为索引，查出目标亮度。提前计算映射曲线，避免逐像素重复计算。
    LUT 以空间换时间，用一个数组存储预计算结果，直接根据颜色去索引映射至目标值。
    创建了 1×256 的 CV_8UC1 表
    https://zhuanlan.zhihu.com/p/604897964
    https://dev.epicgames.com/documentation/unreal-engine/using-lookup-tables-for-color-grading-in-unreal-engine?application_version=5.5&lang=zh-CN
    https://blog.csdn.net/m0_51133195/article/details/154124578
  3. 对比度拉伸：CLAHE 局部直方图均衡化，以增强局部明暗差异，并抑制噪声放大
    ① 图像分块（Tiles）：将图像划分为 M×N 个小块（OpenCV 默认 8×8），每个块独立进行直方图均衡化。
    ② 对比度限制：对每个小块的直方图设置截断阈值（即 ClipLimit），当某一灰度级的像素数量超出该阈值时，超出部分的像素会被均匀分配到其他灰度级中。限制了最大对比度增益，抑制噪声放大与过曝。
    ③ 双线性插值为：避免块拼接产生伪影，对相邻块的结果进行双线性插值，使过渡平滑。
  4. 色彩校正：三维 LUT
    整体调色滤镜，用于修正成像链路偏色，3维 LUT，用 512×512 图片保存一个 64×64×64 个颜色采样点：64 个蓝色切片按 8×8 平铺，每个切片内部是红绿坐标，通过查表和插值得到输出颜色。
  5. 掩膜：显示结果 = 原图×(1-M) + 增强图×M；暗区、反光区，即无效边缘。
    区域 到底是什么 简单做法 为什么排除
    暗区 画面里照明不足、非常暗的部分 计算亮度，低于阈值就标记；例如 Y<20 强行提亮容易把噪声一起放大
    反光区 灯光照在湿润表面，形成的强亮斑 找“非常亮、接近白色”的像素：RGB 三通道都很高 已经饱和的亮斑没有细节可恢复，继续增强只会更刺眼
    “我的优化思路分为计算和数据传输两部分，让 GPU 和 CPU 混合处理。计算方面，暗区、反光区掩膜的生成需要对大量像素重复进行计算和判断，可以用 SIMD 指令在 CPU 上进行并行计算，批量生成掩膜，再由 GPU 执行原图与增强图的逐像素混合。数据传输方面，利用 CUDA 尽可能让图像处理按顺序在 GpuMat 上连续执行，避免每个效果都在 GPU 和 CPU 间反复拷贝。掩膜外接矩形就是必要的 ROI（局部区域），对于需要 CPU 处理的部分计算，仅复制部分图像，再回写 GPU 原图对应区域，减少整帧传输导致的 PCIe 带宽瓶颈。”

“整体的数据传输链路上，原本优化思路，最初设计是优化计算和数据传输两部分，也就是让 GPU 和 CPU 混合处理。在计算上，对于需要大量的复杂 CPU 计算，可以通过 SIMD 指令在 CPU 上进行批量并行计算，然后再由 GPU 执行这个原图的各种特效处理，利用这个 CUDA 让图像尽可能地按顺序在 GpuMat 上连续执行，避免这些处理在 GPU 和 CPU 间反复拷贝。然后还有另外要 CPU 处理的部分计算，可以使用 ROI（局部区域）仅复制部分图像，再回写 GPU 原图对应区域，减少整帧传输导致的 PCIe 带宽瓶颈。其中还准备用 D3D11 的乒乓双缓冲来回输入输出两张纹理进行合成。但后期发现没有这么复杂的需求，就改成了优先采用 CUDA，在显存中连续完成图像处理，并通过互操作将结果交给 D3D11 合成显示；在不支持 CUDA 时，回退 CPU 进行图像处理。CPU 路径对掩膜生成等重复像素计算采用 SIMD 并行优化，并根据掩膜确定 ROI，减少处理范围。并由 D3D11 统一完成原图融合、病灶标注和显示。因为如果用 shader 需要自己编写很多复杂的处理，而 CUDA 可以直接调用 OpenCV 库很多现成的函数。”

互操作的解决方案：消除数据复制
图形互操作的核心机制是：CUDA 能够将纹理直接映射到其地址空间，从而实现：

  • 零拷贝（Zero-Copy）： 数据在 GPU 显存中原地不动。
  • 高速访问： CUDA Kernel 可以直接读取和写入这些图形资源，无需经过 PCIe 总线或主机内存。
    解决了原本频繁的 CPU/GPU 内存 复制（通过慢速的 PCIe 总线）造成的巨大性能瓶颈。

粒子模拟、光线追踪、漫反射之类的复杂计算一般应该也可以用 CUDA 互操作来高效计算吧。
“在光线遍历阶段，尽管相交测试主要由 RTCore 处理，但次级光线的生成、着色计算以及尤其是包含复杂材质交互（如次表面散射光谱渲染）的光路计算，仍需回归到 CUDA 的通用计算单元进行处理。这种“RTCore 负责几何求交，CUDA 负责着色与逻辑”的分工模式，已成为 UnrealEngine5 的 Lumen 全局光照系统与 Unity HDRP 的光线追踪模块的标准架构”
GPU 并行计算在游戏引擎中的集成与应用：基于 CUDA 架构的系统性综述

病灶模型接入

基于 ONNX Runtime 接入息肉与异常黏膜检测模型，完成输入缩放、颜色转换、归一化、推理及结果解析；根据画面变化控制模型执行时机，并对连续帧检测框的位置和置信度进行平滑。

固定输入为：未增强1080P RGB 原图 → 双线性等比例缩放 → 居中填充到 640×640，背景填充灰色 RGB=(114,114,114) → Float32 除以 255（归一化） → NCHW [1,3,640,640]（批次、通道、高、宽）

拉伸与留边：检测框怎么回到原图

  • 拉伸：改变图片比例填充正方形，x、y 分别直接按比例还原。

  • 留边：英文是 letterbox，看电影时，上下出现黑边，就是类似的思路。还原时先平移（向上-y轴）再乘比例。
    对同一张 1920×1080 图像：
    ① 宽和高都缩小为原来的 1/3：1920×1080 → 640×360
    这时图像没有被拉变形，但高度只有 360，距离模型要求的 640 还差：640−360=280

    ② 把这 280 平分到上下：上下各补 140。

输出解析

输出固定为 Float32 [1,N,6]，每一行依次是 x1,y1,x2,y2,score,classId。坐标是 640×640 输入上的像素边界，score 已为 0～1 分数，classId 以整数值放在浮点 Tensor 中：0=息肉候选，1=异常黏膜候选。模型图不包含 NMS，客户端先去除非有限数、非法类别和无面积框，保留 score≥0.30，再做类别内 IoU=0.50 的 NMS，最后逆 letterbox 回原图。

NMS 是在同一帧中去掉高度重叠的重复检测框；跟踪是把不同帧的结果关联成同一个目标，两者不同。本项目明确做类别内 NMS：息肉候选之间相互抑制，异常黏膜候选之间相互抑制，不跨类别删除。

病灶跟踪与标注

根据检测框重叠关系、中心点距离和运动方向关联连续帧病灶，为同一目标维护跟踪标识；将病灶框、类别、置信度和检查时间绘制为独立图层，并保留原始无标注图像。

把 IoU、距离、方向得分乘权重再相加，计算把框认作同一个目标的“代价”，得分越低越好（成本）。

  1. 怎么判断两个框是不是同一个目标？
    判断依据 通俗理解 为什么有用
    框的重叠程度 新框与旧框是不是大部分压在一起？ 两帧间移动不大时，同一个目标的框通常重叠很多
    中心点距离 两个框的中心离得近不近？ 移动稍大、不再重叠时，也能继续比较
    运动方向 它原来往右走，新框是不是也往右了？ 有多个相邻目标时，辅助区分
  2. IoU：重叠程度，IoU = 交集面积 ÷ 并集面积
  3. 预测：假设同一个目标的中心位置连续变化，第一次：x=100，过了 0.1 秒：x=110，程序估计它每秒向右移动 100 像素。那么再过 0.1 秒，先猜：下一次 x ≈ 120。新检测回来后，再看它是否在预测位置附近。
    预测中心=上次中心+速度×经过时间，
  4. 多目标匹配
    匹配代价，越小越好 A B
    T1 0.1 0.4
    T2 0.2 0.9
    如果 T1 先挑，选了最便宜的 A，T2 就只剩 B：总成本 = 0.1 + 0.9 = 1.0，独立贪心。
    如果整体考虑，让 T1 选 B、T2 选 A：总成本 = 0.4 + 0.2 = 0.6
    第二种搭配整体更合理（匈牙利算法）。
  5. 轨迹保留生命周期：目标短暂消失时，不能马上删除，会导致同一目标 ID 不断变化，不利于连续记录。
    轨迹状态固定为：新候选 → 连续两次检测命中后确认 → 未匹配时进入丢失状态 → 距最后匹配超过 500 ms 删除。候选时用虚线提示。
    采用两种期限进行平滑：
    时间规则 做什么
    200 ms 显示期限 距最近真实检测太久，就隐藏框，避免一直画旧框
    500 ms 内部保留期限 暂时保留轨迹记录，目标重新出现后仍有机会接回旧 ID
  6. 平滑：位置和置信度平滑。
    平滑检测框抖动，新显示值=(1-α)×旧显示值+α×新观测值，α=0.3时，新显示位置 = 旧显示位置×0.7 + 新位置×0.3
    根据运动速度动态调整检测间隔，目标快速移动时要减少平滑，让框更快追上；目标静止时再加强平滑。
    例如静止时 τ=80 ms，中心位移超过上次框对角线的 10% 时 τ=20 ms，加快追随；换轨迹或场景切换直接重置。
    显示置信度用 τ=200 ms 单独平滑，原始分数另存，检测阈值仍作用于原始分数。

影像采集与渲染

通过采集卡接入内镜主机视频信号，处理设备占用、采集格式变化和信号中断；基于 D3D11 完成离屏渲染与颜色转换，将原始画面、增强结果和病灶标注按图层顺序合成显示。

驱动将采集卡注册为 Windows 视频采集设备可以使用 WinRT MediaCapture 通过 SharingMode 选择共享只读或独占控制，检查初始化、启动结果。

  1. 设备占用：“原本的已经在用的预览软件已经打开采集卡，工作站需要同时读取画面，因此优先尝试共享只读，获取设备当前输出，不修改源配置；共享初始化失败后，先清理本次资源，再尝试独占控制。而如果需要调整设备的分辨率、帧率或源格式，则直接申请独占控制。因为两个软件会竞争采集设备的控制权限，需要设置独占控制和共享只读两种模式的降级兼容策略。”
    “然后启动失败时，程序仍可能已经创建部分资源，像注册回调之类的，会导致与下次尝试的冲突，需要先取消订阅和释放引用(帧对象)什么的”。
    步骤 对应 API 做什么
    1. 找设备 DeviceInformation::FindAllAsync 枚举设备名称和 ID；现有 getCameras 使用这条路径
    2. 配置会话 MediaCaptureInitializationSettings 设置 VideoDeviceId、SharingMode、MemoryPreference 等
    3. 打开会话 InitializeAsync 按配置尝试连接设备，失败时处理异常
    4. 选择视频源 FrameSources 找到彩色视频源；需要改源格式时必须先有控制权限
    5. 创建读取器 CreateFrameReaderAsync 为选中的源建立读取入口
    6. 订阅通知 FrameArrived 注册新帧到达回调，并保存订阅 token
    7. 启动读取 StartAsync 检查返回状态是否为 Success
    8. 持续取帧 TryAcquireLatestFrame 在通知回调中尝试取得最新帧，空结果直接返回
    微软官方WinRTFrameReader标准流程:
    ① 寻址（Enumerate）：在庞杂的系统设备列表中，拿到目标摄像头的“唯一身份证”（DeviceID）。
    ② 配置与初始化（Initialize Settings）：向系统提交一份“需求清单”，决定接下来是用 CPU 还是 GPU 处理数据，是独占硬件还是与其他软件共享。
    ③ 定位数据源（Find Source）：从摄像头提供的多个功能镜头中，精准剥离出“彩色画面（Color)”的数据流。
    ④ 建立阅读器（Create Reader）：为选定的镜头建立一个专属的数据接收队列，并决定当程序处理不过来时该怎么办。
    ⑤ 订阅事件（Subscribe Event)：挂载一个 FrameArrived 回调函数，告诉系统有新画面时通知程序。
    ⑥ 开机拉流（Start)：正式命令摄像头开始录像。
    ⑦ 拆解快递（Frame Arrived Callback)：获取最新帧，进行格式转换，并提取为 C++ 能读写的裸内存。
    ⑧ 关机清理（Cleanup）：停止数据流，释放摄像头设备，销毁阅读器。
  2. 采集格式变化：应用收到的分辨率、像素格式或帧率改变，需要更新对应缓冲、纹理、颜色转换及坐标映射。
    “先关闭帧分发入口，协调在途采集回调结束。清理未执行的预览和推理任务，等待正在使用旧缓冲的任务完成；录制端按顺序处理完旧帧，渲染端确认 GPU 不再使用旧资源。随后更新缓冲、纹理和编码配置，全部就绪后再恢复新格式帧分发，避免新旧格式数据混用或提前复用缓冲。”
  3. 信号中断：设备暂时无法提供有效的内镜画面，例如 HDMI 断开或主机切换输出。程序需要提示无信号、隐藏旧标注并记录中断时间。
  4. 离屏渲染：先把结果写进自己的纹理，不直接写窗口后台缓冲。这样截图、示教和预览可复用同一结果，输出尺寸不随窗口改变。
    多消费者情况可以保留原始结果和多种效果的叠加合成处理，配合 D3D11 的乒乓双缓冲，可以连续处理保留多个纹理。

编码推流模块

  1. NVENC/AMF/x264 硬编软编回退：NVENC 使用 NVIDIA 视频编码硬件；AMF 是 AMD 媒体接口，这里用于硬件编码；x264 用 CPU 做 H.264 软件编码。可以都输出 H.264。

  2. 码控模式切换：

    模式 直观解释 使用时要知道
    CBR 恒定码率 尽量围绕固定带宽预算输出 适合带宽约束，但并非每毫秒完全相同；复杂画面可能更糊
    VBR 可变码率 简单画面少用，复杂画面多用 通常结合目标与最大码率控制波动
    CQP 恒定质量因子 固定量化参数，压缩强度较固定 码率随内容变化；不等于所有场景的感知画质完全相同

  3. 低延迟策略：关闭 B 帧 ctx->max_b_frames=0;；缩减编码器缓冲区大小 ctx->rc_buffer_size = bitrate /2;，使编码器在网卡时立刻降低画质，而不是堆积帧；编码器低延迟参数优化（开启低延迟模式）；减小网络数据包大小和缓冲。

    RTMP 调优：RTMP 用来把 FLV 音视频流经网络持续发送到服务器。TCP 保证有序可靠传输，但丢包后的重传等待可能带来延迟。
    在 StreamMuxer::applyNetworkoptions 中设置 rw_timeout=3000000，单位微秒，即 3 秒；开启 flush_packets=1 每个包写出后，刷新底层 I/O 缓冲，减少数据留在 FFmpeg 缓冲里的等待，强制立刻发包；开启 tcp_nodelay=1 禁用系统的 Nagle 算法合并小包的等待，让系统有包就发，不为了节省头部开销而“拼凑大包”，降低发送延迟；将 FFmpeg 内部的包缓冲队列 fifo_size 从默认的一万砍到50，一旦网络拥堵立刻让上层感知并降码率。

  4. 拥塞降码率与丢非关键帧：

    本次检查时的队列包数 当前代码执行什么
    大于 30 先删除队列中非关键视频包；只有实际删掉至少一个包，才尝试把当前目标码率乘 0.7
    21～30，包括 30 把当前目标码率乘 0.95
    1～20，包括 20 这次检查不调整目标码率
    等于 0 若当前目标低于用户配置值，则乘 1.02，逐步恢复，最多恢复到用户配置值

    两套拥塞控制：第一套根据队列包数量；第二套根据处理一张视频帧，包括相应的格式处理、同步、编码和编码包入队总耗时。

    规则 算的是什么 数字例子
    单次耗时大于 200 ms，或平滑耗时大于 150 ms 判为拥塞 不是队列超过 20/30 的那套判断
    前两次连续拥塞 该控制器自己的当前目标×0.7 2500→1750→1225 kbps
    连续拥塞次数超过 2 该控制器自己的当前目标×0.5 1225→612.5 kbps，再受上下限约束
    符合恢复条件 每次增加 50000 bit/s，即 50 kbps 1500→1550 kbps，不是增加 50%

  5. 断线重连：“发送线程发现网络写包失败后，会标记对应输出不可用，暂时跳过这一路发送，并周期性尝试关闭旧 IO、重新打开原推流地址。连接成功后清除失败标记，恢复后续包的发送。重试由出队包计数触发（30个）；另外，网络连接恢复和媒体播放恢复是两回事，还要验证媒体头、编码参数、关键帧和时间戳是否正确恢复。”

  6. 音视频同步：
    用已处理音频样本累计数作为同步参考，并用视频 PTS 计数推算视频时长。
    计算 PTS 以实现同步。DTS 由编码器生成，在关闭 B 帧的情况下，理论上两者相同。

    “把音频样本数和视频帧计数换算成秒，以音频为参考。视频落后就重复画面补时间，视频超前就跳过输入等待；阈值是一帧时长，单次最多补五帧。”

端云内容模块

  1. 处理场景/素材云端同步：客户端把对象序列化为 JSON 发送给云端，或把云端 JSON 还原成本地对象实现设置同步。

    “项目使用 Qt 的 JSON API 做场景数据转换。保存时，手动把场景和元素的属性写入 QJsonObject，把多个元素组织成 QJsonArray，再通过 QJsonDocument 转成 JSON 文本，包装成 HTTP 请求发送。加载时先解析云端 JSON，再读取素材 ID、类型和布局属性，获取或创建素材源，重新创建 SceneItem 并恢复位置、尺寸和层级。JSON 序列化负责数据表达，上传、下载和应用到本地对象这些流程合起来才是这里的同步。”

  2. 验证码/密码/企微扫码三种登录鉴权：
    “密码登录提交账号密码、租户 ID 和客户端标识等，组成 JSON，发送 POST 到 /auth/login；企微扫码通过 WebEngine 加载二维码页面，拦截并捕获携带 Code 的重定向链接，再提取 Code 提交给业务后端换取本系统 Token。验证码部分实现了接口封装，具体短信服务商不是我接入的。登录成功后统一保存 Token，由 HttpManager（定义了 RESTful动作 get/post/put/del）在后续请求中附加 Authorization 请求头，获取用户资料和权限，供后续使用。”

    序列化：网络层将 C++ 的 QJsonObject 对象序列化为紧凑的 JSON 字符串（QJsonDocument:Compact）。

  3. Bearer Token：是一种加密字符串，它代表的是用户的身份或权限。服务端通过验证这个 Token，确认请求的发起者具备访问某些资源的权限。QString finalToken=token.startsWith("Bearer")？token：("Bearer"+token);强制为 Token 加上了 Bearer 前缀。

    ① 替代传统明文认证，提升安全性：是服务器生成的 “临时凭证”：令牌本身不包含用户敏感信息（如密码），即使泄露，攻击者也无法反向推导出用户账号密码；令牌可设置短期有效期，降低泄露后的风险范围。
    ② 简化后续请求的鉴权流程，提升效率：用户只需在首次登录时提交真实凭证（如账号密码），后续向服务器发起请求时，无需重复提交敏感信息，只需在 HTTP 请求头中携带 Bearer Token 即可，流程极大简化。
    ③ 灵活控制权限范围（配合令牌内容设计）：服务器可在生成令牌时，将用户的权限信息（如 “只能访问订单列表，不能修改订单”）、用户 ID 等数据加密存储在令牌中（如 JWT 格式的 Bearer Token），后续验证令牌时可直接解析出权限，实现 “精细化权限控制”。

  4. 创建者与 authList 权限模型：SceneAuthEntry 中有 userId、query、add、edit、del；云端字段对应 queryAuth、addAuth、editAuth、deleteAuth。它类似“每个场景一张授权名单”。

    ① 编辑/删除先检查对应全局权限，可直接放行。
    ② 当前用户是创建者，或者创建者为 0，直接放行。
    ③ 遍历 authList，找到用户，按本次操作检查对应值是否为 1。
    ④ 没匹配则拒绝。
    例：张三创建场景，李四只有 query=1、edit=0，可以查看但不能通过这项对象授权编辑。不过李四若拥有全局编辑权限，会在第一步被放行，因此不能只看 authList。

  5. 共享布局与个人偏好两级内容合并：平台提供默认布局配置序列化成 JSON 保存到云端，提供给多个用户使用的同一套场景设置，并存储个人偏好设置，将各个元素的位置、尺寸等信息从共享配置读取，而设备、组件的选择保留个人偏好。

  6. 素材下载热替换：异步下载和替换，使用 emit 通知管理器替换源文件

端云 AI

  1. 旁路采样：当系统从摄像头或麦克风采集到原始数据时，数据流被一分为二：
    ① 主路(Main Pipeline):传给m_recordcontroller进行高强度编码（如H.264/AAC），并推流给观众。
    ② 旁路(AI Bypass):传给_aiBridge，进行低分辨率降采样和切片，供Al审核使用。
    分一路根据 PTS 每秒采样 2 帧（2FPS），对音频分片（每2秒一个 PCM 切片），通过 HTTP 上传字节流QByteArray。
  2. 视频缩放与音频重采样：使用 sws_scale 把 NV12 转为 YUV420P，硬编码输出为 480×480；主采集是 48 kHz 双声道 Float32，云端需要 16 kHz 单声道 S16。同时改变采样率、声道数和数值格式，转换结果写入 FIFO。
  3. 按时间切片上传：FIFO 累计够 32000 个样本，取出 64000 字节作为一片 2 秒 PCM，交给上传回调。未够一片的数据继续留在 FIFO。
  4. 队列丢弃策略：视频队列在入队前若 size()>5，或音频入队前若 size()>100，丢最旧任务。丢旧视频使分析更接近当前状态；音频更重连续性，所以阈值更大。保证实时性>完整性。
  5. 端云状态轮询与自动停播逻辑： 默认 1000 ms 轮询云端状态，下播或 roomId 失效时自动停播。

处理崩溃报告与调用栈还原

  1. dump 和调用栈分别是什么：
    调用栈记录函数调用关系：例如用户开相机 → 初始化设备 → 创建 reader → 出错。机器运行时主要留下地址，符号文件把地址对应到函数名、源码文件和行号。

    dump 是出错时线程、寄存器和部分内存等现场数据；PDB 是某次构建的符号映射。dump 保存现场，PDB 帮助解释现场。 不是拿到任何同名 PDB 都能还原，必须匹配实际 EXE/DLL 的构建。

  2. 仓库实际做了哪些步骤
    注册未处理 SEH、CRT 无效参数、纯虚函数、std::terminate 和信号等入口；出错后建立 CrashDumps 目录，调用 MiniDumpWriteDump 写 dump，再输出文本栈。

    文本栈使用 SymInitialize 加载符号，StackWalk64 沿栈遍历，SymFromAddr 查函数名，SymGetLineFromAddr64 查行号。g_IsInCrashHandler 用于避免处理器递归进入，最后终止进程。

    “访问冲突”常指读写无效地址；“纯虚调用”可能与对象生命周期异常有关。但异常名只告诉你症状，不能直接断定根因。最顶层可能只是崩溃处理函数，真正错误还要看异常上下文和之前调用。

  3. Release 为什么还要保留符号
    CourseStudio.pro 在 Release 中增加 /Zi 与 /DEBUG，便于保留调试符号。Release 仍可以优化；有符号不等于变量都完整保留，优化会造成内联或变量不可见。

    一个能讲清的排查过程：先确认版本与匹配符号，再打开 dump，找异常线程、异常地址和调用链，检查对象生命周期、参数和并发时序，结合复现步骤验证假设。不能只看到某库在栈顶就断言库有 bug。

    当前在崩溃进程内使用 Qt、堆分配和符号解析，严重内存损坏或死锁时报告仍可能失败；手动捕获上下文的 terminate/signal 路径也未必保留最初抛错点。应讲“提升现场可诊断性”，不要承诺所有崩溃都能完整还原。

“我用 dump 保留现场，用对应构建的 PDB 还原函数和源码位置，再结合异常线程及日志查生命周期和并发问题。Release 也生成符号，但优化和现场损坏会限制可见信息。”

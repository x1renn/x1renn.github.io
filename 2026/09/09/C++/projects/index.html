音视频基础

AVFrame 是未压缩的图像或音频样本，AVPacket 是编码后的数据包。编码器可能缓存数据，所以一次输入不一定立即对应一个输出包。

PTS 是应该展示的时间，DTS 是解码所需的时间；有帧重排时二者可能不同。time_base 是一个时间刻度的长度：time_base=1/30 时 PTS=60 表示 2 秒；音频若以 1/48000 为刻度，PTS=96000 也表示 2 秒。必须换到同一单位再比较。

GOP 是一段有参考关系的画面序列。关键帧提供恢复解码的重要入口，常见 P 帧会依赖参考帧。IDR 还承担刷新参考关系的作用，不能把所有“标记为关键”的帧都不加区别地当作万能恢复点。
https://www.cnblogs.com/samirchen/p/7071824.html

实时美颜模块 OpenCV

  1. 双边滤波 距离近 + 颜色相近的像素权重大；距离远或颜色差异大的像素权重小。

  2. LUT 以空间换时间，用一个数组存储预计算结果，直接根据颜色去索引映射至目标值。

  1. warpAffine 仿射变换，双眼两个点可以给出三个信息：中点代表位置，距离代表大小，连线方向代表平面内角度。计算 dx=rightEye.x-leftEye.x、dy=rightEye.y-leftEye.y，再取 angle=-atan2(dy,dx)×180/π，斜率即倾斜角度。

渲染管线模块

  1. YUV 中 Y 表示亮度，U/V 表示色度。人眼对亮度细节更敏感，因此可以保留更多亮度信息、减少色度采样。4:2:0 表示图像中每个 2×2 像素区域有 4 个 Y，配一组 U/V。
    NV12 把所有 Y 放在一个平面，再把 U/V 交错放在第二个平面。YUV420P 则是 Y、U、V 三个独立平面。两者都是 4:2:0，但字节排列不同。

  2. 色彩矩阵：把 RGB 换成 Y、U、V。8 位 Limited Range 的 Y 映射到 16～235，色度映射到 16～240。
  3. 色彩分级：整体调色滤镜，3维 LUT，用 512×512 图片保存一个 64×64×64 的颜色立方体：64 个蓝色切片按 8×8 平铺，每个切片内部是红绿坐标。
  4. 读写同一张纹理冲突黑屏问题：A 已经绑定为输出 → 又尝试把 A 绑定为 shader 输入时，D3D11 会检测到冲突，将冲突的输入槽置为 NULL，而不是按要求绑定 A。
    “同一资源不应同时作为 shader 输入与渲染输出。绑定冲突时 D3D11 可能将输入槽置空，随后采样得不到预期画面。需要清理绑定，并加互斥锁，让多级滤镜交替读写两张纹理，避免输入输出冲突。”
    项目的 convertRGBtoNV12 在绑定输入前，先做这件事： 这里的“清空”是清空输出槽的绑定，不是擦掉纹理 A 的画面，也不是释放纹理。
    随后才把 A 接到输入槽，并选择另一个输出目标： 使用Ping-Pong 双缓冲，使每一步都有独立的输入和输出
    如果连续做磨皮、美白、锐化，每一步都需要“读上一轮结果、写新结果”。

采集模块

  1. 摄像头共享与独占：有2级，前1级可共享读不调整帧源配置；后一级使用独占控制，能控制帧源配置。每次申请失败要先清理资源。
    微软官方WinRTFrameReader标准流程:
    ①寻址（Enumerate）：在庞杂的系统设备列表中，拿到目标摄像头的“唯一身份证”（DeviceID）。
    ②配置与初始化（InitializeSettings）：向系统提交一份“需求清单”，决定接下来是用CPU还是GPU处理数据，是独占硬件还是与其他软件共享。
    ③定位数据源（FindSource）：从摄像头提供的多个功能镜头中，精准剥离出“彩色画面（Color)”的数据流。
    ④建立阅读器（CreateReader）：为选定的镜头建立一个专属的数据接收队列，并决定当程序处理不过来时该怎么办。
    ⑤订阅事件（SubscribeEvent)：挂载一个FrameArrived回调函数，告诉系统有新画面时通知程序。
    ⑥开机拉流（Start)：正式命令摄像头开始录像。
    ⑦拆解快递（FrameArrivedCallback)：获取最新帧，进行格式转换，并提取为++能读写的裸内存。
    ⑧关机清理（Cleanup）：停止数据流，释放摄像头设备，销毁阅读器。
  2. WGC 帧池，是 Windows 截取窗口或屏幕时，用来暂存、复用采集画面的缓冲区集合，负责在“系统产生画面”和“程序处理画面”之间交接数据。帧池是一组复用的帧缓冲区。
    ①确定截取哪个窗口
    ②创建两缓冲帧池
    ③注册回调，然后启动采集，“有新帧时，调用 onFrameArrived”
    ④系统产生新画面，触发回调，系统将采集画面放入帧池，触发 FrameArrived 事件，这个通知在帧池内部工作线程触发
    ⑤回调中调用 TryGetNextFrame()，真正取得帧
    ⑥从帧里取得纹理，再提供给渲染
    frame → Surface → ID3D11Texture2D → 创建或复用 SRV
    然后在锁内更新 m_currentSRV。后续通过 getTexture() 取得这个 SRV，作为读取画面的入口。
    ⑦用完采集帧，结束借用，允许缓冲复用。帧的有效使用结束后，缓冲可以归还给系统，装下一张画面。C++/WinRT 包装对象在析构时释放自己持有的接口引用。
    局部 frame 离开作用域 → 包装对象释放引用 → 最后一个帧引用消失 → 帧生命周期结束 → WGC 回收缓冲。
  3. 屏幕采集窗口最小化边界：是指在创建帧池前判断 size.Width<=0 || size.Height<=0 失败时返回，避免用非法尺寸创建资源，是启动阶段的防御。
  4. WASAPI：音频捕获客户端（CaptureClient）
    ① 环境准备（COM Initialization)：初始化底层组件环境。
    ②发现设备（DeviceEnumeration)：查找系统中的麦克风或扬声器。
    ③ 激活音频客户端（ActivatelAudioClient)）：与指定的硬件设备建立连接。
    ④ 协商格式与初始化（Negotiate&Initialize）：获取设备的音频格式（采样率、位深），并告诉系统我们要怎么用它（独占还是共享？要不要录系统声音？）。
    ⑤ 获取捕获服务（Get lAudioCaptureClient)：拿到真正用来“抽水”的数据读取工具。
    ⑥ 启动数据流（Start)）：命令声卡开始录音。
    ⑦ 捕获大循环（TheCaptureLoop）：在一个死循环中，不断检查有没有新数据。如果有，拿出来转换格式；拿完必须把缓冲区还给系统。
    ⑧停止与清理（Stop&Cleanup）：停止流，释放所有资源。
  5. 音频统一浮点32位格式便于乘音量、混合和重采样。
  6. 静音包实现按原包长填 0，保持时长连续，不删除以防止和视频错位。

编码推流模块

  1. NVENC/AMF/x264 硬编软编回退：NVENC 使用 NVIDIA 视频编码硬件；AMF 是 AMD 媒体接口，这里用于硬件编码；x264 用 CPU 做 H.264 软件编码。可以都输出 H.264。

  2. 码控模式切换：

    模式 直观解释 使用时要知道
    CBR 恒定码率 尽量围绕固定带宽预算输出 适合带宽约束，但并非每毫秒完全相同；复杂画面可能更糊
    VBR 可变码率 简单画面少用，复杂画面多用 通常结合目标与最大码率控制波动
    CQP 恒定质量因子 固定量化参数，压缩强度较固定 码率随内容变化；不等于所有场景的感知画质完全相同

  3. 低延迟策略：关闭 B 帧 ctx->max_b_frames=0;；缩减编码器缓冲区大小 ctx->rc_buffer_size = bitrate /2;，使编码器在网卡时立刻降低画质，而不是堆积帧；编码器低延迟参数优化；减小网络数据包大小和缓冲。
    RTMP 调优：RTMP 用来把 FLV 音视频流经网络持续发送到服务器。TCP 保证有序可靠传输，但丢包后的重传等待可能带来延迟。tcp_nodelay=1 请求禁用 Nagle 算法合并小包的等待，让系统有包就发，不为了节省头部开销而“拼凑大包”，降低发送延迟。

  4. 拥塞降码率与丢非关键帧：

    本次检查时的队列包数 当前代码执行什么
    大于 30 先删除队列中非关键视频包；只有实际删掉至少一个包，才尝试把当前目标码率乘 0.7
    21～30，包括 30 把当前目标码率乘 0.95
    1～20，包括 20 这次检查不调整目标码率
    等于 0 若当前目标低于用户配置值，则乘 1.02，逐步恢复，最多恢复到用户配置值

    两套拥塞控制：第一套根据队列包数量；第二套根据处理一张视频帧，包括相应的格式处理、同步、编码和编码包入队总耗时。

    规则 算的是什么 数字例子
    单次耗时大于 200 ms，或平滑耗时大于 150 ms 判为拥塞 不是队列超过 20/30 的那套判断
    前两次连续拥塞 该控制器自己的当前目标×0.7 2500→1750→1225 kbps
    连续拥塞次数超过 2 该控制器自己的当前目标×0.5 1225→612.5 kbps，再受上下限约束
    符合恢复条件 每次增加 50000 bit/s，即 50 kbps 1500→1550 kbps，不是增加 50%

  5. 断线重连：“发送线程发现网络写包失败后，会标记对应输出不可用，暂时跳过这一路发送，并周期性尝试关闭旧 IO、重新打开原推流地址。连接成功后清除失败标记，恢复后续包的发送。重试由出队包计数触发（30个）；另外，网络连接恢复和媒体播放恢复是两回事，还要验证媒体头、编码参数、关键帧和时间戳是否正确恢复。”

  6. 音视频同步：
    用已处理音频样本累计数作为同步参考，并用视频 PTS 计数推算视频时长。
    计算 PTS 以实现同步。DTS 由编码器生成，在关闭 B 帧的情况下，理论上两者相同。
    “把音频样本数和视频帧计数换算成秒，以音频为参考。视频落后就重复画面补时间，视频超前就跳过输入等待；阈值是一帧时长，单次最多补五帧。”
